### E.5.3:5 - Archetypal Grounding (System / Episteme)

| Family | `U.System` illustration | `U.Episteme` illustration |
|-------|------------------------|---------------------------|
| Core | Definition of `U.System` and boundary invariant. | Definition of F‑G‑R assurance components. |
| Tooling | The “Reference system‑profile” checks boundary flow and *imports* Core invariants. | The “Episteme‑scoring routine” calculates R‑score and *imports* Core characteristics. |
| Pedagogy | A tutorial uses the system‑profile to model a pump and *imports* the profile and Core term. | A case study explains R‑score evolution and *imports* the scoring routine and Core term. |
| **Forbidden** | Core pattern importing measurement script. | Core pattern importing R‑score web dashboard. |

A guide teaches the boundary invariant from Core and links to a profile checker for practice. Readers can establish a boundary from the published rule with the checker unavailable. One exercise accepts any report satisfying a separately published format. Another generator can supply it if its report meets the acceptance conditions. A separate exercise requires a report signed by the named checker in the agreed format. A retained signed report can satisfy that exercise if it covers this case, edition and acceptance conditions, even after the checker closes. If the exercise commissions a new check or a fresh signature, establish whether the named checker or an accepted compatible edition can supply it when required. If the new check is unavailable, report which requirement can no longer be met and why. This can complete an inquiry about dependencies. When changing the exercise is part of your commission or standing duty, make a revision within your authority or take the proposal to those entitled to decide. Readers can continue to work from the Core definition. Recheck their explanation if its definition or the argument used to teach it changes.
